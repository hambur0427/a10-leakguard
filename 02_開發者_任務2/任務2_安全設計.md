# 任務 2：安全設計

範圍：兩個開關後的功能 `one_click_revoke`、`severity_notify`。
圖：見 `security_diagram.svg`。

## A. 身分驗證與授權

### 決策表

| 項目 | 選擇 | 理由 |
|---|---|---|
| 登入 | OAuth 2.0 / OIDC，以 GitHub 帳號登入 | 專題資料本來就在 GitHub，不用自己存密碼；可直接取得使用者所屬 repo |
| Session | 伺服器端 session（cookie 只放隨機 session ID，設 `HttpOnly`、`Secure`、`SameSite=Lax`） | 需要「撤銷」類高風險動作，伺服器端 session 可立刻作廢；JWT 一旦簽發較難即時撤回 |
| 角色模型 | RBAC 加「資源擁有者」檢查 | 角色決定能做哪類動作，擁有者檢查決定能對哪個 repo 做 |
| 高風險動作 | 撤銷前再次確認並寫稽核紀錄（audit log） | 撤銷會中斷使用該金鑰的服務，需可追溯 |

### 角色

| 角色 | 說明 |
|---|---|
| `member` | 一般成員，可看自己有權限的 repo 的通報 |
| `repo_owner` | 某 repo 的負責人，可處理該 repo 的通報 |
| `admin` | 管理開關、通知規則、檢視稽核紀錄 |

### 權限矩陣（伺服器端檢查）

| 動作 | member | repo_owner（自己的 repo） | repo_owner（別人的 repo） | admin |
|---|---|---|---|---|
| 檢視通報 | 僅自己有權限的 repo | 可 | 不可 | 可 |
| 一鍵撤銷（`one_click_revoke` ON） | 不可 | **可** | 不可 | 可 |
| 一鍵撤銷（`one_click_revoke` OFF） | 不可 | 不可（API 回 404 或 403） | 不可 | 不可 |
| 調整通知分級規則 | 不可 | 不可 | 不可 | 可 |
| 切換開關 | 不可 | 不可 | 不可 | 可 |

> 原則：隱藏按鈕不是存取控制。開關 OFF 時，撤銷 API 本身也必須拒絕。這是 QA 的測試案例。

### 檢查順序（每個請求）

1. 是否已登入（session 有效）
2. 開關是否 ON（對該使用者）
3. 角色是否允許此動作
4. 是否為該 repo 的擁有者
5. 通過才執行，並寫稽核紀錄

任一步失敗都在伺服器端拒絕。

## B. 軟體組成分析（SCA）

做法：在 repo 啟用 GitHub Dependabot（設定檔見 `dependabot.yml`），同作業 9。

### 高風險相依套件處理表（依 Dependabot 警示填寫）

> 下表是範本。實際的套件與嚴重度，請以你們 repo 的 Dependabot 警示為準，不要憑空填。

| 套件 | 版本 | 警示嚴重度 | 處理 | 理由 |
|---|---|---|---|---|
| （例：flask） | （目前版本） | （Dependabot 顯示） | 升級 | 有修補版本且相容 |
| （例：某間接相依） | （版本） | （嚴重度） | 替換 | 已停止維護 |
| （例：某開發用套件） | （版本） | （嚴重度） | 接受 | 只在開發環境，不進正式部署；記錄到期重評日 |

判斷順序：有修補版本就升級；無修補且已停止維護就替換；影響不到執行環境才接受，並寫下理由與重新檢查日期。

## C. 機密管理

| 項目 | 決策 |
|---|---|
| 存放位置 | GitHub Secrets 與 environments（`staging`、`production` 各自獨立） |
| 哪些是機密 | OAuth client secret、session 簽章金鑰、通知用 SMTP 或 webhook 憑證、各服務的撤銷 API token |
| CI/CD 注入 | GitHub Actions 以 `secrets.*` 於執行時注入環境變數，不寫入檔案、不印在 log（見 `ci.yml`） |
| 程式碼規則 | 絕不把機密寫進程式碼或 `flags.json`；設定檔只放非機密值 |
| 防外洩 | 開啟 GitHub secret scanning 與 push protection，被偵測到會擋下推送 |
| 外洩後 | 立刻撤銷並輪替，這也是本專題要做的功能的使用情境 |
