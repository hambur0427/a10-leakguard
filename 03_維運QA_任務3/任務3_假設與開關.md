# 任務 3：假設與功能開關

## 假設 1：一鍵撤銷（`one_click_revoke`）

| 項目 | 內容 |
|---|---|
| 改動 | 在通報頁加上「一鍵撤銷並產生輪替清單」按鈕，取代手動到各服務後台撤銷 |
| 使用者 | 已登入、且是該 repo 負責人（`repo_owner`）的成員 |
| 預期影響 | 負責人更快撤銷外洩的金鑰 |
| 成功指標 | 兩週內，從通報到撤銷完成的時間中位數縮短 40% |
| 護欄指標 | 誤撤銷率（撤銷後被要求復原）不超過 5%；因金鑰失效造成的服務中斷事件不增加；撤銷 API 錯誤率不上升 |

**完整句子：** 我們相信，為 repo 負責人加上「一鍵撤銷並產生輪替清單」按鈕，會讓外洩金鑰更快被撤銷。當通報到撤銷的時間中位數在兩週內縮短 40%，就代表我們是對的。護欄：誤撤銷率不超過 5%，服務中斷事件與 API 錯誤率不上升。

**決策規則（實驗開始前先定）：** 時間中位數下降 ≥ 40% 且護欄都沒變差 → 開放到 100%。沒有明顯變化 → 關閉並移除開關。護欄任一項惡化 → 立刻用緊急開關關閉。
**樣本與期間：** A/B 各 50%（`rollout: 50`），跑 14 天；中途就算看起來有效也不提早停止。
**怎樣會證明我們錯：** 時間中位數下降不到 40%，或誤撤銷率超過 5%。

## 假設 2：依嚴重度分級通知（`severity_notify`）

| 項目 | 內容 |
|---|---|
| 改動 | 高風險即時通知，中風險每日摘要，低風險每週摘要，取代全部即時通知 |
| 使用者 | 所有會收到通報的 repo 負責人 |
| 預期影響 | 高風險金鑰更快被處理，通知疲勞降低 |
| 成功指標 | 兩週內，高風險通報 24 小時內被處理的比例提升 25% |
| 護欄指標 | 中、低風險通報 7 天內未處理的比例不上升；漏通知數維持 0；通知退訂或關閉率不上升 |

**完整句子：** 我們相信，把通知依嚴重度分級，會讓高風險金鑰更快被處理。當高風險通報 24 小時內的處理率在兩週內提升 25%，就代表我們是對的。護欄：中、低風險通報的未處理比例、漏通知數與退訂率都不變差。

**決策規則（實驗開始前先定）：** 高風險 24 小時處理率提升 ≥ 25% 且護欄都沒變差 → 開放到 100%。沒有明顯變化 → 關閉並移除開關。出現漏通知 → 立刻關閉。
**樣本與期間：** A/B 各 50%，跑 14 天，不提早停止。
**怎樣會證明我們錯：** 處理率提升不到 25%，或任何高風險通報沒有被通知到。

## 開關設定

方式：設定檔 `flags.json` 加上程式碼 `flags.py`。

```json
{
  "one_click_revoke": {"enabled": true, "rollout": 100},
  "severity_notify":  {"enabled": true, "rollout": 100}
}
```

- `enabled`：緊急開關（kill switch），設為 `false` 對所有人關閉
- `rollout`：0–100，開放給多少百分比的使用者
- 以 `sha256(旗標名:使用者ID) % 100` 分組，同一使用者每次都在同一組

### 如何切換

1. 直接改 `flags.json`，重新整理頁面即可（每次請求都重新讀取）
2. 管理員呼叫 `POST /admin/flags/<flag>`，body 為 `{"enabled": false}` 或 `{"rollout": 20}`

`rollout` 接受 0–100 的整數或整數字串；非整數、布林值、null、超出範圍等不合法輸入回 HTTP 400，且不寫入開關或成功稽核紀錄。省略 `rollout` 則保留原值。

### 撤銷指標（issue #16）

每筆 alert 的 `created_at` 為 UTC ISO 8601 建立時間；成功撤銷時記錄 `revoked_at` 與 `revoke_duration_seconds`，稽核紀錄也帶耗時。耗時定義是「告警建立到成功撤銷」的秒數，並非 API 執行延遲。

管理員登入後可讀 `GET /admin/metrics`，JSON 回傳 `revoke_count`（成功撤銷數量）及 `median_revoke_duration_seconds`（耗時中位數，秒）。無樣本時回傳 `0` 與 `null`；偶數樣本取中間兩值的平均。拒絕或重複撤銷不計入；非 admin 回 403，未登入回 401。

目前僅統計此程序記憶體中的告警；重啟會重建示範資料，不能據此宣稱已量得跨程序、兩週或真實服務商的撤銷成效。正式實驗仍需持久化告警與撤銷資料。

### 開關的類型、負責人與到期日（避免旗標債）

| 開關 | 類型 | 負責人 | 到期日 | 實驗結束後 |
|---|---|---|---|---|
| `one_click_revoke` | 實驗型（兼具緊急開關用途） | 維運/QA | 12/15 | 有效則刪開關、功能常駐；無效則連功能一起移除 |
| `severity_notify` | 實驗型 | 維運/QA | 12/15 | 同上 |

這些欄位已寫在 `flags.json` 的 `type`、`owner`、`expires`。開關不是存取控制：撤銷 API 的權限一律在伺服器端檢查，`flags.json` 也不放任何機密。

### 建議的逐步釋出（選做）

| 階段 | `one_click_revoke` rollout | 觀察 |
|---|---|---|
| 1 | 10% | 誤撤銷率、API 錯誤率 |
| 2 | 50% | 通報到撤銷的時間 |
| 3 | 100% | 持續監控護欄指標 |

`one_click_revoke` 會實際作廢金鑰，風險較高，起始比例建議低。

## 各角色補充

- **設計師**：UI 變體見下方 ON 與 OFF 的差異；使用者流程為「收到通報 → 開通報頁 → 按撤銷 → 看輪替清單」，OFF 時改為「手動到服務後台撤銷」。
- **維運**：旗標存放在 `flags.json`；緊急開關為 `enabled: false`；監控各狀態的撤銷成功率與錯誤率（規劃中）。
- **QA**：測試案例在 `test_leakguard.py`，涵蓋 ON、OFF、切換，以及「按鈕被隱藏時，直接打 API 也被擋」。

## 兩種狀態的差異

| | ON | OFF |
|---|---|---|
| `one_click_revoke`：負責人頁面 | 顯示按鈕 | 不顯示，改為「手動處理」 |
| `one_click_revoke`：直接呼叫撤銷 API | 負責人成功；其他人 403 | 一律 404 |
| `severity_notify`：通知管道 | 高即時、中每日、低每週，並依顏色分級 | 全部即時，無分級 |
